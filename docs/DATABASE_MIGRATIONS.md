# Database Migrations

PostgreSQL is the intended public-v2 source of truth. Alembic owns staging and
production schema changes; the application does not call `create_all` or run
ad-hoc column migrations in those environments.

## Additive design

Revision `a509623c6959` creates a separate public schema alongside the legacy
tables. The public identity table is `app_users`; it is deliberately separate
from legacy `users` so an upgrade never changes or replaces the original user
rows. The old `goals` table remains untouched and the new model uses
`tracked_goals`.

The backfill sequence is:

1. Back up the database.
2. Run `python -m alembic upgrade head`.
3. Run `python ../scripts/backfill_legacy_to_public_v2.py` without flags.
4. Review row counts and sample mappings.
5. Run the same command with `--apply` in staging.
6. Re-run the dry run; new-row counts should be zero.
7. Enable new reads and then writes only through their feature gates.

The backfill maps legacy `users` to `app_users` by unique Telegram ID and maps
`raw_entries` to `work_logs` by unique `legacy_raw_entry_id`. It never deletes
or updates a legacy row.

## Commands

Run commands from `backend/`:

```powershell
python -m alembic current
python -m alembic upgrade head
python -m alembic check
python -m alembic history
```

Create a reviewed future migration:

```powershell
python -m alembic revision --autogenerate -m "schema update"
python -m alembic upgrade head
python -m alembic check
```

Never run autogenerated migrations without reviewing constraints, indexes,
foreign-key deletion rules, defaults, and downgrade behavior.

## Test database

The test URL is mandatory when `APP_ENV=test`, and configuration validation
rejects a test URL equal to `DATABASE_URL`.

```powershell
docker compose --profile test up -d postgres_test
$env:APP_ENV = "test"
$env:DATABASE_URL = "postgresql://unused:unused@localhost:5432/not_used"
$env:TEST_DATABASE_URL = "postgresql://pr_agent_test:pr_agent_test_local@localhost:5433/pr_agent_test"
Set-Location backend
python -m alembic upgrade head
python -m alembic check
pytest -q tests/test_migrations.py
```

The CI migration job uses a dedicated ephemeral PostgreSQL service and runs
upgrade, schema drift detection, downgrade, and a second upgrade.

## Downgrade policy

Revision `a509623c6959` drops only the new public-v2 tables in reverse
foreign-key order. It does not drop or modify legacy tables. A downgrade will
remove data written only to public-v2 tables, so it requires a backup and an
explicit rollback decision. In normal production incidents, roll the
application back while leaving the additive schema in place.

Do not downgrade after public-v2 writes are enabled unless the data has been
exported or a forward fix is impossible.

## Deployment order

1. Take and verify a database backup.
2. Deploy code with public feature flags disabled.
3. Run `python -m alembic upgrade head` as a one-off release command.
4. Run `python -m alembic check`.
5. Start the web and worker processes.
6. Run health and tenant-isolation smoke tests.
7. Enable reads, then writes, for the beta cohort.

Running `upgrade head` again is safe and does not recreate tables.

The current Render Blueprint is intentionally configured for the free,
single-instance service: its start command upgrades the database before
starting Uvicorn. Before increasing the service above one instance or moving
database work into a separate worker, switch the migration command to Render's
pre-deploy command so only one release process performs migrations. Render
offers pre-deploy commands on paid web services, private services, and
background workers.
